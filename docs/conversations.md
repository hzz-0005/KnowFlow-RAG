# C1：持久会话与有限追问理解

本阶段把多轮入口接到原有 RAG 链路，不替代文档解析、切块、重排、图增强、来源核验与评测。总路线见 总体后续方案书（本地研究记录，未随公开包分发）。C2 已补澄清衔接、原始条件传递和[首稿生成预算](answer-budget.md)；全链路预算、任务拆解、任务状态和长期记忆仍待实施。

## 数据怎样保存

- PostgreSQL `conversations`：账号、知识库、标题、轮次修订号、当前执行权与过期时间、最近完成轮次和引用文档身份。
- `conversation_turns`：原问题、独立检索问题、改写状态、请求幂等标识、执行状态、完整答案与引用、错误类别、来源版本、时间。
- 浏览器 sessionStorage 只记现有登录凭证及当前知识库/对话 ID；回答和历史不以浏览器缓存作为真值来源。刷新从服务端恢复。新窗口可通过对话选择器打开同账号知识库的记录。
- 对话按账号与知识库隔离。引用身份也是线索；权限检查仍在每轮查询执行。没有新增长期用户画像或跨知识库记忆。

## 一次追问怎样执行

1. 新一轮先检查所属账号、知识库、请求指纹和 `expected_revision`。同一请求 ID 加同一内容只返回已保存的记录；内容变更或修订号过期返回 409。
2. 短事务锁住会话，保存 pending 轮次与执行权后提交；不把这个锁持有到模型调用结束。
3. 无历史且无指代触发词的首问直接查询；无历史但含之前/it/continue等词时，也由有界解析器区分完整独立首问和缺对象输入，不能仅据词表强制澄清。有可用历史时，不依赖代词词表，先判断承接、独立新话题或需要澄清。读取最近 8 轮 completed / needs_clarification 记录，以最近一次已验证的独立话题为默认承接边界，普通追问选择该边界之后最多 3 个完整用户意图；待澄清时必带原问题、已收到的补充及澄清请求，另选最多 2 个已完成意图。总输入载荷限制为 3000 个本地 tokenizer token；普通模式最近一轮完整意图为必需项，装不下就要求重述，不能跳过它换更早话题；其他可选历史仍整条跳过、不截半句。这里不是生成模型的整个上下文窗口预算，也未验证该 tokenizer 与所有远程模型一致。
4. 指代解析只收到用户意图与仍匹配来源版本的文件名/章节；不提供旧助手回答、旧节选或评测答案。保存原问题与解析结果；检查返回格式、实际引用轮次及数字约束。疑义或解析失败时询问用户，不猜对象。
5. 独立检索问题进入原有查询流程：改写、混合检索、可选重排/图检索、引用展开、生成与依据核验。旧答案不充当新证据。
6. 独立事务核对执行权和修订号后完成写入。超时、失败、中断有持久状态；过期 pending 在下一次请求时回收。失去执行权的迟到结果不能覆盖新轮次。

来源版本使用文档 SHA-256 与更新时间。只有查询前、完成时均一致的文档才保存为可复用身份；后续更新、删除或离开已处理状态的来源身份不进入追问载荷。旧用户提问仍是用户曾表达的意图，并不因其保留而获得事实有效性。

查询改写另有 [执行诊断与数字保护输入](query-rewrite.md)：区分接口、响应完整性与内容校验，记录实报 usage、原因和原问题回退。原问题数字字面值显式提供给改写器，但仍严格逐条校验，不自动补数字；截断输出不采用。旧轮次缺原因保持未知，不根据重跑填补。该步骤不等于会话指代解析，也不保证完整语义保真。

### C2 首个小包：澄清衔接

`conversation-reference-v2-clarification` 将待澄清意图保存在轮次 `resolution.pending_intent`，由最新语义轮次派生，没有第二份独立状态或新表。第一次缺对象时保存原问题；随后即使用户只回复一个名称、没有“它”等指代词，也会进入澄清解析。重复澄清保留完整用户补充；旧澄清轮没有该字段时，从其原问题兼容恢复。

- 刷新、重复请求及同账号重新打开会话后，仍从数据库读取同一待澄清事项。失败或中断的尝试不消耗它，也不把失败输入视作已接受条件；用户重试须再次提交该补充。
- 补充足够时，生成独立问题并重新检索；解析结果必须引用实际待澄清轮次。数字只能来自当前输入及明确引用的意图；不允许借未引用轮次的数字。
- 用户改问完整独立问题时，解析器可返回 standalone，但问题必须与本轮输入逐字一致、历史引用为空；完成该轮后旧澄清结束。是否确为完整新话题仍依赖模型判断，不能据此保证任意话题切换正确。
- 待澄清载荷本身超过预算时，不截断后猜测；明确要求重新表述完整问题，保存 requires_restatement 标记。下一轮不再装入过长旧意图，只能接受完整新问题或继续澄清；原轮次记录仍在数据库。
- 模型失败、非法轮次引用、数字校验失败均继续澄清，不绕过证据核验、不静默返回模型猜测。格式/数字校验不是否定、范围、日期更正的完整语义校验。

## 接口与页面

### C2：原始条件与检索改写分离

`conversation-reference-v3-user-constraints` 在解析成功时，从本轮原话与明确引用的历史用户记录重建 `intent_context`。用户原文、历史引用身份和继承的原始条件一并保存；模型返回的同名字段不被采用。下一次追问可继承这些原始输入，不只继承此前可能失真的检索改写。历史助手答案仍不进入该路径。

旧v3有近期历史时仍依赖“改为/只看/排除”等启发式信号。v5开始有历史就判断，覆盖“保留多久？”与“And in production?”等省略输入，独立话题必须返回当前输入原文且引用列表为空。v6补默认话题边界，v7补版本有效的来源身份。当前为 `conversation-reference-v8-cold-intent`：含指代提示词的首问增加一次分类，显式传递`no_prior_intents`，完整命名的问题可独立检索；缺对象仍澄清，禁止构造不存在的历史引用。没有触发词的冷首问仍走快速路径，残缺输入识别不完整。数字更正须保留本轮全部数字，`current_numeric_tokens` 将其显式列入解析输入，被替换值应表为排除项；仍用原有严格数字校验，不事后补数，也不据字面存在宣称极性或范围正确。

v8源于固定中英文开发首问被确定性`no_context`分支误拦截。新增分类沿用完整提示预算、15秒异步超时和整轮准入，无隐式重试；失败或截断仍澄清。v5/v6/v7独立轮次继续可作为话题边界，不回填旧轮次或重跑旧答案。新提示改变了合同版本，历史与v8不能冒称同协议比较。固定场景与检查方式见[多轮开发场景](../evaluation/conversation_v1/README.md)，独立复核仍未建立。

v6来自一次真实页面失败：已切换到独立新产品后，普通追问仍被旧产品条件干扰而要求澄清。只把受支持v5–v8已验证standalone、空历史引用且无继承意图的已完成轮次认作默认话题边界；未知旧版本或字段不一致时不猜边界。当前待澄清意图仍保留；较早用户记录仍在数据库，但默认不装入这次解析载荷。需要返回更早话题时，应明确对象和条件；任意跨话题远距回忆尚未实现。topic_scope计数仅覆盖本次已读的近期窗口，不能当全历史排除数量。

独立问题仍用于召回、查询扩展和原有排序。相关性检查、回答生成与依据复核另收到结构化用户意图：本轮原话、引用到的历史用户输入、仅供参考的检索线索；明确本轮更正优先，历史输入不是文档事实。没有另加模型审核步骤，但现在有历史的独立新问题也会多一次上下文解析，不能宣称成本与时延不变。一次解析不自动重试，等待使用min(15秒, query_rewrite_timeout_seconds)的异步取消，不能打断同步初始化而保证严格墙钟上限。原始文本传递完整不保证模型理解正确；错误改写仍可能影响候选召回和排序。

解析只接纳正常stop响应；失败或非法内容进入澄清，记录封闭原因码、是否发起请求、供应商实报用量和提示/正文指纹。超时缺用量为未知，不作零成本。最近意图超预算单列`recent_intent_budget_exceeded`，要求完整重述；详情可观察实际承接或新话题决策和调用成本，旧轮次字段不回填。设计依据与一次真实控制中的失败/修正见 本包记录（本地研究记录，未随公开包分发）。

该内部上下文用 Pydantic PrivateAttr 从会话处理器传入，不接受请求 JSON 注入，不进入请求指纹序列化；原单轮接口没有上下文时按原问题处理。完整原始意图计入解析阶段的 3000 本地 token 载荷预算，不截断原始条件来硬凑容量；首稿生成另外按共享实际提示合并计算原始意图、证据与输出预留，其他调用阶段仍有独立预算。相关轨迹保存在轮次 resolution 与 query_plan.intent_context；详情的“检索问题与原始条件”可安全查看本轮原话、历史条件和检索线索，切回其他轮次会清空旧详情。

本轮参照 LlamaIndex / LangChain 官方信息流与社区故障线索（本地研究记录，未随公开包分发），借鉴结构并做本项目约束下的适配，没有引入框架依赖。自动检查、真实页面及限制见 本包记录（本地研究记录，未随公开包分发）。

输入区默认一行，随内容自动增高，最多四行；超过四行时在框内滚动，删减后自动回缩。发送按钮位于输入框右侧；检索、召回和引用展开共用下方一行工具栏。

- `POST/GET /api/v1/knowledge-bases/{id}/conversations`：创建/列出最近 50 个会话。
- `GET /api/v1/conversations/{id}`：默认最近 10 轮，`before` 加载更早记录，单页最多 20 轮。
- `POST /api/v1/conversations/{id}/turns`：普通查询参数加 UUID `request_id`、整数 `expected_revision`；响应为持久轮次，含状态与可空 `response`。
- 页面支持新建空对话、切换、刷新恢复、查看更早记录。主区域约 90% 用于聊天与底部输入；用户消息是右侧蓝色气泡，模型在左侧显示完整安全 Markdown；发送后立即显示本地等待状态。回复底部“查看详情”打开对应轮次答案、引用和独立检索问题。诊断各有彩色标题、边框和展开正文，解析提示独立分组。知识库/对话切换后不展示旧请求的迟到结果。
- 原单轮 `/knowledge-bases/{id}/query` 保留，原离线评测接口和历史协议不变。

执行状态与答案质量不同：completed 只说明查询返回了结果，结果可能是合理拒答，也可能仍存在模型核验误差。工程测试数量不代表问答成功率。

本包发现并修复了引用衔接问题：完整通过逐单元审核的保留块可能没有自带内联引用，而原有引用所在块被过滤。`validated-block-sources-v1` 只给这类保留块补充其审核证据中已逐字验证、属于本轮上下文的 UUID 来源标记；不复用拒绝块的引用，不改写表格/图的内部内容，不修正已有伪造标记来绕过 API 拒绝。绑定记录含原块正文 SHA-256 与来源 ID，可在回答核验详情查看。审核仍是模型判断加字面引文检查，并非独立语义金标。

幂等防止已知同一请求重复收费，不能保证服务器崩溃时远程模型恰好执行一次；中断可产生已经计费但本地未确认的调用。浏览器不会自动重跑过期请求。C1 列表目前仅显示最近 50 个会话，旧会话仍在数据库，后续补列表分页、归档/删除与保留策略。

## 澄清辅助（2026-10-26）

在需要补充对象时，聊天与回答详情会显示当前知识库最多五份已处理文档。文件名按确定顺序展示，超过五份时提示在右栏查看其余文档；这是可用性列表，未经相关性排序，不是检索结果或引用。只有一份文档也不自动判定“它”的对象。请填写文件名、具体对象或完整问题，列表不会替用户发送消息。

上下文解析协议v10沿用v5–v9已确认的独立话题边界。因记忆停用、修订、过期等导致旧指代不可用时，服务器提供原因说明，连续澄清仍保留。完整独立新问题可以切换话题，不继续带入旧原因。解释原因与展示文件列表均不新增模型调用；原历史记录不覆写。实际失效原因依赖可读到的历史依赖，缺失历史不能事后编造原因。

当前尚未完成任意复合问题的“部分回答+澄清”、任意业务对象消歧或多轮语义质量验收。证据见`review/clarification-hints-20261026/README.md`。

### 部分回答首版（后续v13）

复合问题可以提议一个无需未知部分结果的独立查询，按原RAG链检索并核验。所有非待澄清文字均保留，来源/数字/依赖和预算校验未通过就不派发。返回中partial_answer标明独立查询、未查询范围、full_request_complete=false；无论部分是否有答案，整轮仍待澄清，保存/刷新不丢未决条件。有引用的部分答案不是完整任务成功；refused=false不能替代完成状态。

当前还没有“另一个对象”的实体候选检索机制。合理方向是先按当前范围查候选、排除已指明实体，唯一合理剩余对象说明依据，多候选列名确认；不能把只召回一个当成全库唯一。此缺口与A2一起推进，原B3自然题及任意复合任务质量仍待复核。首两次负结果和一个合成开发控制见`review/partial-clarification-20261026/README.md`。
