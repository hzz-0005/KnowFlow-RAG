# 本地运维

默认端口只绑定127.0.0.1：前端8080、API8000、数据库5433。公网部署需要自行配置TLS、网络访问策略、独立数据库凭据与资源预算；首版不承诺生产SLA。

## 启动、日志、停止

原生解析：`docker compose up -d --build`。Docling路径每次使用相同覆盖参数：`docker compose -f compose.yml -f compose.pdf.yml up -d --build`。

查看 `docker compose ps`、`docker compose logs --tail 100 api`、`docker compose logs --tail 100 frontend`。不要把含个人文档或凭据的日志直接贴进公开issue。

`docker compose stop`保留数据。`docker compose down`会移除容器/网络但保留命名卷；不要添加删除数据卷的选项，除非明确要清空对应测试项目。

更新源码后先备份，重建镜像再启动。API启动会升级Alembic；回退应用镜像不等于数据库迁移能逆向回滚，首版升级前应先在备份副本验证。

## 备份与恢复

需要一起备份数据库与uploads-data上传卷。数据库保存账号、文档元数据/切片/关系/会话/记忆；上传卷保存源文件和解析缓存。只有一个部分不能完整恢复项目。

数据库建议使用容器内`pg_dump -Fc`先写文件，再用`docker cp`复制到宿主机；避免旧PowerShell把原生二进制stdout重定向成文本。备份不要提交GitHub。上传卷可在停止摄入后用可信容器只读挂载并归档；备份目录权限由本机管理。

恢复应使用单独Compose项目、新卷和未占用端口，导入数据库及上传卷后核对文档/切片/会话数量与原文件哈希，最后再做一次有引用问答。不要覆盖正在使用的库。首版的隔离软件契约测试可以验证迁移/持久化，不能自动证明你的真实备份可恢复。

## 常见故障

- Docker未运行：启动Docker后再检查compose ps，不要新建一套空卷假装数据恢复。
- 端口占用：停止冲突服务，或编辑本地端口映射；不要修改容器内部服务名和数据库地址。
- 无API key/模型ID不支持：填本地.env，对照供应商实际可用模型；重建/重启API使配置生效。健康检查通过不代表供应商凭据有效。
- 改了embedding模型/维度：原索引不可直接混用。先备份，在新知识库中重新摄入验证。
- PDF缺字/错序：查解析报告、切片及原页；原生解析不做OCR，Docling也不保证所有版面正确。不要把换问法当解析修复。
- 处理重启中断：持久批任务按租约恢复并有重试上限。旧单文件及图谱后台接口未全部持久化，查看明确状态后再操作，不承诺远程请求恰好一次。
- 登录失效：使用自己的原账号重新登录；新账号有独立知识库，空列表不代表旧数据被删除。
