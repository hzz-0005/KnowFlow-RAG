# 复杂文档处理：调研结论与实施清单

更新：2026-10-22。本文是依据当前代码审查和官方资料形成的实施方案；下列待办不代表已经上线。

用户明确要求面向批量导入、不依赖逐文件人工审批。最新官方调研及修订的研发顺序见 [批量自动解析与分块方案](batch-ingestion-plan.md)。人工查看切片仅用于研发抽查；尚未实现的自动质量路由、结构/token 分块与持久队列需要明确区分。

此前已交付聊天格式、Markdown 表格和本地 Mermaid 图表展示，以及复杂 PDF 调研、原解析器审计和 16 类验收规格。本阶段已接入可选的本地 Docling 服务、中文 OCR、表格结构、有序来源块、逐页质量报告和原页区域预览；明确编号的跨页引用索引与候选展开已接入；通用多证据知识关系、隐含指代与图中箭头视觉解释仍未实现。

已补上[每次检索片段的相关性检测](retrieval-confidence.md)：全部 top-k 候选有分级、理由、支持引文及采用状态；有 12 类/24 对固定模型回归，以及伪造引文、检查失败、上下文截断、引用越界等自动回归。当前后端在实际 Docker 镜像内 81 项、前端 17 项测试通过。新增“查看切片”，直接展示实际入库切片或解析块，可分页、按关键词/页码筛选、查看来源区域。详见 [PDF 解析与检查](pdf-parsing.md)。相关性等级和解析状态均不冒充校准后的概率。新增单页 OCR 对照，独立保存候选、文字/数字差异与历史基线标记，不自动覆盖索引。

## 1. 当前短板及处理方法

| 问题 | 当前实现及风险 | 确定采用的处理方法 | 验收证据 |
|---|---|---|---|
| 扫描页、图片页 | 已接入 Docling OCR，记录原文字层和索引块字符数；native 模式仍有明确未核验提示 | 扩充低清晰度、旋转和混合页样本，不用文字数量冒充准确率 | 两份中文受控扫描样本的编号、周期、百分比和对象名称通过；混合样本已在页面检索与定位 |
| 多栏、文本框、页眉页脚 | 已保存 Docling 正文树顺序及坐标，页眉页脚保留为检查块并退出正文索引 | 继续逐页核验顺序和内容覆盖，分类器判断仍可能出错 | 真实九页复杂 PDF 已完成转换；不能把每页有文字当阅读顺序正确的证明 |
| 字体编码与解析依赖 | 复杂样本在项目环境提示 CFF 字体解码缺少 fontTools，另一解析器版本还出现替换字符 | 记录依赖版本和解码异常；补齐字体支持并与原页对照，无法还原时转 OCR/视觉路径 | 比较关键字符、编号和原页，不把替换字符为零当完整性证明 |
| 标题层级、列表、代码 | MD 有标题路径；PDF 以页分段，DOCX 只保存当前标题 | 统一章节树；块保留父子、前后、类型与来源，不把页作为语义边界 | 多级标题、列表上下文、代码边界回归 |
| 大表、跨页表、复杂表头 | PDF 已保存单元格与跨行跨列范围，行组携带表头、单位和表注；DOCX 尚为基础路径 | 核验多层表头和数字对应，后续实现跨页续表匹配 | 真实样本检测到 5 个表格；存在结构不代表每个单元格都正确，跨页合并待实现 |
| 流程图、嵌套图、箭头 | 当前未使用图像输入，无法从文字抽取中保证箭头方向 | 保存原图/裁剪与页坐标；用 MiMo 视觉路径提取节点、分组、箭头、标签，保留不确定状态；视觉解释与原文引文分开 | 正向/反向边、虚线与实线、嵌套分组、无箭头邻近节点的正反例 |
| 相邻页延续 | 图抽取批次不跨 PDF 页，关系必须落在单一切片 | 以章节和段落组织上下文；带入相邻块，允许多块证据组成一条关系 | 句子跨页和代词跨页的证据覆盖 |
| 隔多页才解释关系 | 已建明确编号的章节/表格/图注引用索引，唯一匹配时最多两跳展开；隐含指代、误分类与语义关系仍有限制 | 先扫结构，建立章节、图号、表号、编号条款索引；解析显式引用并按需展开，不能仅靠固定邻居窗口 | 第 2 页定义、第 8 页说明、再引用第 4 页条件的完整证据链 |
| 指代、缩写、同名实体 | NFKC、大小写、空格归一；不是真正实体消歧 | 保存别名、类型、文档范围、定义出处；规则优先，LLM 处理有证据的歧义；多个候选时保持未消解 | 中英文别名合并，同时避免同名不同对象误合并 |
| 一条关系需要多处证据 | Relation 只有 source_chunk_id 和一段 evidence；分发阶段丢弃跨片段关系 | 新建关系证据关联表，一条关系关联多个块/切片及引文；保留证据角色、抽取版本与来源类型 | 每条边可回到全部证据，非法跨文档/知识库引用被拒绝 |
| 多层关系与错误推理 | 两跳检索不等于完整推理；邻接和共现不能证明关系 | 区分文档结构图与知识图；按问题在预算内展开路径，每一步都验证证据；推断路径不冒充原文直接断言 | A→B、B→C 的路径回答必须同时引用两步，不能捏造 A→C 原文关系 |
| 否定、条件、版本冲突 | 引文存在只证明来源定位，不证明谓词含义正确 | 关系保存条件、否定、时间和适用版本；矛盾不直接覆盖；回答说明适用条件或冲突 | “仅测试环境”“旧版规则”“未批准”“可能”的反例 |
| 切片数量和速度 | 1000 字符/120 重叠，图批次 4000 字符；无结果缓存和断点续建 | 结构分块、模型 tokenizer 预算、必要时语义细分；缓存按内容/解析器/提示词/模型版本；持久任务、重试、进度、限流 | 文档变化仅重算受影响部分；中断可恢复，不固定 16 批 |
| 多格式 | 实际支持 TXT、MD、DOCX、文字 PDF | 后续依次接入图片、HTML、CSV/XLSX、PPTX，共用文档结构，但分别保存页面/工作表/单元格/幻灯片位置 | 每种格式经过真实上传、引用定位和问答验收后再标为支持 |
| 回答难读、内部 JSON 外露 | 问答没有强制 JSON，但页面原先只展示纯文本 | 正常聊天格式；安全渲染 Markdown、表格和 Mermaid；内部图抽取仍用结构化 JSON | 普通问答、表格、图表、引用、无证据拒答与恶意 HTML 回归 |
| 评测只看简单资料 | 原有小规模检索集不覆盖复杂解析、回答忠实度 | 增加真实复杂文档和可控正反例；分别测解析、关系、证据集、回答，记录成本与耗时 | 按失败类别展示前后对照，不能用“构建成功”代替准确率 |

## 2. 选型决定

优先验证 **Docling 结构化 JSON + 我们独立实现的检索/图谱逻辑**。原因是它的文档模型包含结构树、阅读顺序和位置来源，适合统一中间层；这不是已经测得它在我们的文档上效果最好。[Docling 文档模型](https://docling-project.github.io/docling/concepts/docling_document/)

复杂 PDF 的对照解析器选择 MinerU，比较 OCR、版面、表格的真实效果。暂不同时默认跑两个引擎，避免成本翻倍且难以定位改进来源。[MinerU 官方仓库](https://github.com/opendatalab/MinerU)

Docling 可通过独立服务适配，不把模型权重和推理依赖直接塞进 API 进程。适配器接收结构化 JSON，同时保存原始转换结果；转换失败、部分成功、超时必须分别处理。[Docling Serve 接口](https://github.com/docling-project/docling-serve/blob/main/docs/usage.md)

现有 `mimo-v2.6-pro` 官方支持图片 URL 与 Base64 输入，可复用现有供应商配置建立视觉解析路径。当前 KnowFlow 仍只调用了文字路径；视觉能力需要实际请求和图表回归确认。[MiMo 图片理解](https://mimo.mi.com/docs/zh-CN/quick-start/usage-guide/multimodal-understanding/image-understanding)

Qwen embedding 继续用于文本语义表示和召回。它不会自动恢复 PDF 阅读顺序、表格结构或箭头关系。OCR、视觉解析、关系抽取、embedding 是不同阶段。

## 3. 中间数据与迁移

拟新增 `DocumentBlock`：文档 ID、稳定块 ID、块类型、正文、章节路径、父块、顺序、页码、坐标、解析来源、原图引用、质量告警。表格另存结构化单元格、表注和标题；不同格式另存工作表/行列/幻灯片定位。解析器未提供置信度时记为未知，不能伪造一个分数。

拟新增 `DocumentLink`：来源块、目标块、链接类型（前后、父子、章节引用、表/图引用），并记录已解析、歧义、未找到的状态。显式编号引用也可能重复或指向其他文档，需要范围消歧。

拟新增 `RelationEvidence`：关系 ID、块/切片 ID、准确引文或视觉区域、证据角色、来源类型。旧单片段关系作为单条证据迁移。`source_chunk_id` 可暂时兼容旧读路径，但新回答不能只使用其中一条证据。

文本索引和引用正文分开：标题、表头、必要定义可以加入检索上下文，但必须保留实际证据的位置；生成的图片说明不能伪装成原文逐字引用。

“先通读全篇”在工程上分为两步：第一步扫描全篇结构、定义、编号和显式引用；第二步对候选关系组织相关上下文，再抽取和验证。不会假定一次全篇 LLM 调用就理解并记住所有关系。文档特别长时，同样需要层级索引与预算控制。

## 4. 切片和检索的具体规则

1. 先按结构类型切分：段落、标题、代码、列表、表格、图片分别处理；页码只作为来源。
2. 根据 embedding tokenizer 与上下文预算调整长度，不按整篇固定片数。长段落才细分；表格优先按行组拆并带表头。语义分段是可评测的增强项，不是每篇必须再调 LLM 通读。
3. 小块负责命中；命中后按需补父章节、相邻延续、被引用的图表/条款。展开范围记录在检索追踪里，受总 token 和引用数量限制。
4. 图抽取使用与证据相关的上下文包；保留多个来源，不再要求一条关系的所有信息出现在同一块。
5. 回答前检查证据链是否齐全，涉及数值时同时取回表头、单位与条件；不足时明确缺哪一步。生成图表只可表达有证据的关系或数值。

参考的是方法而非整套框架依赖：Docling 的结构与 token 结合切分、LightRAG 的段落/表格上下文处理，以及 GraphRAG 关系关联多个文本单元的来源设计。它们不能单独保证跨页指代正确。[Docling 切分](https://docling-project.github.io/docling/concepts/chunking/)、[LightRAG 段落切分](https://github.com/HKUDS/LightRAG/blob/main/docs/ParagraphSemanticChunking.md)、[GraphRAG 输出模型](https://github.com/microsoft/graphrag/blob/main/docs/index/outputs.md)

## 6. 如何证明有改善

解析层：文字覆盖与漏页告警、阅读顺序、表头/单位保留、表格结构、图箭头方向。OmniDocBench 可作为真实版面与解析指标的参考，但它不替代我们的跨页关系和 RAG 评测。[OmniDocBench](https://github.com/opendatalab/OmniDocBench)

关系层：人工标注的实体消歧准确率、关系 Precision/Recall/F1、全证据覆盖率、错误合并和未消解数量。证据逐字存在只是来源校验，不是关系语义正确的充分条件。

检索层：现有 Recall@K、MRR、nDCG 之外，加“一个问题所需证据是否全部取回”的完整证据集召回；同时看进入生成上下文的证据，避免只在候选池中命中。

回答层：关键事实正确、每个可核验断言有依据、引用确实支撑该断言、缺证据时拒答。区分解析丢失、检索漏召回、上下文截断、模型乱编和引用不支持。LLM 评分只辅助，保留人工抽查与反例。

实验固定语料、问题、模型版本、top_k 和预算，记录耗时、token、API 花费；依次比较当前基线、结构解析、引用展开、图增强。先报告真实结果，再决定优化方向，不提前写“准确率 99%”。

## 7. 当前边界

任何方案都不能保证任意脏文档零丢失。可交付的目标是：尽量保留、可追溯、能发现漏失/歧义、证据不足不编造，并用失败用例持续回归。手写、模糊扫描、极复杂图、无明确指代的长距离关系仍可能需要人工校对。

当前可上传格式仍为 TXT、MD、DOCX、PDF。PDF 的本地结构化解析与 OCR 需通过 `compose.pdf.yml` 启用；基础模式仍为原生文字提取。上游工具支持更多格式，不等于 KnowFlow 已支持。[Docling 格式列表](https://docling-project.github.io/docling/usage/supported_formats/)

## 8. 后期优化登记（用户补充，不改变当前开发阶段）

- 常用办公格式：XLSX、CSV/TSV、PPTX、HTML 等；按格式保留工作表、表头、单元格、公式缓存状态、幻灯片和章节位置。旧版 DOC/XLS/PPT 需单独转换和验收，不能只放开上传后缀。
- 跨文件证据链：通用的问题分解、分步检索、实体键关联与消歧、缺失证据补查、完整证据集检查；业务示例仅用于解释和回归，不写成人事或年假专用逻辑。
- 制度和规则修订：保留生效时间、适用范围、明确修订对象和来源；支持条款级修改及冲突提示，不把上传时间当效力顺序。
- 结构化计算：表格精确筛选、关联、汇总和日期计算使用受控工具；分别引用原始数据、规则和计算依据。
- 验收增加同名对象、旧版/未来生效、局部修订、单位不一致、缺失条件和跨领域案例；分别测关联、证据完整性、版本选择、计算和拒答。

以上为后期优化项。当前已推进至批量结构分块、来源核对、明确编号的跨页展开，以及检索/回答/图谱质量验证。指标范围与当前边界见 [质量验证](quality-evaluation.md)。
